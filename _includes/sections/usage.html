Using it

Record once, commit, replay

Your system under test only needs one thing: the VCR's base URL. In record mode the VCR forwards to the real service and hands back the real response; in playback mode it answers from the tape with no network. The API is the same fluent builder in every language, in that language's own spelling.

Python — playback
import servirtium, urllib.request
 
with servirtium.playback("tapes/climate_api.md") \
        .redact_credentials().pretty_json() \
        .port(0).start() as vcr:
    body = urllib.request.urlopen(
        f"{vcr.base_url}/api/v1/countries").read()
    assert vcr.last_kind is servirtium.Outcome.OK
Python — record
with servirtium.record("tapes/climate_api.md",
        "https://climatedataapi.worldbank.org") \
        .redact_credentials().pretty_json() \
        .port(0).start() as vcr:
    urllib.request.urlopen(
        f"{vcr.base_url}/api/v1/countries").read()
    vcr.commit()   # only a commit writes the tape

A recording is written only by Commit(). Discard() drops it. Closing, disposing or dropping a record VCR with neither writes no tape and raises (Python's VcrError, .NET's and Java's VcrException, an error from Go's Close() and Rust's close(), and so on), so a test that fails part-way can no longer mint a tape that later replays as the truth. The scoped helpers in each language discard the recording when their block raises. Playback is unchanged: closing just stops it.

JavaScript / TypeScript
const vcr = Vcr.record('tapes/climate_api.md', upstream)
  .redactCredentials().port(0).start()
try {
  await callTheService(vcr.baseUrl)
  vcr.commit()
} catch (e) { vcr.discard(); throw e }
Java — playback
try (VcrServer vcr = Vcr.playback(
        "tapes/climate_api.md")
        .redactCredentials().port(0).start()) {
    callTheService(vcr.baseUrl());
    assertEquals(Outcome.OK, vcr.lastKind());
}

What the engine does for you

One implementation behind every binding. The full list, with behaviour, defaults, examples and links to each feature's docs and tests, is the feature reference.

Credentials stay off the tape

RedactCredentials turns Authorization, cookies and API-key headers into numbered tokens (Bearer AUTHORIZATION_1, COOKIE_1) and matches them on presence in playback. RedactHeader, RedactQueryParam and RedactJsonField name what else to scrub, and named secret callbacks choose a token per request. The live test still sees the real bytes.

Volatile values

A rule such as request body: <a:MessageID>urn:uuid:{% raw %}{{messageId}}{% endraw %}</a:MessageID> turns ids, timestamps and Date headers into tokens ({% raw %}{{messageId-1}}{% endraw %}), so a re-record of an unchanged conversation is byte-identical. Playback matches any live value there and echoes it back where the token reappears. The rules ride in the tape's own ## Volatile values block.

The VCR's own address

{% raw %}{{baseUrl}}{% endraw %}, {% raw %}{{request.host}}{% endraw %} and {% raw %}{{request.scheme}}{% endraw %} are filled from the live request, in responses and now in requests too, so a tape replays on any port. In record mode, RewriteUpstreamBase keeps a service that writes its own absolute URLs (TFS's location service, a HATEOAS API, a paging nextLink) from sending the client around the recorder.

Substitution and placeholders

Substitute rewrites a value in the replayed response (a marker of your own, such as a vault host, filled at playback; .NET's Placeholder does the request and response sides of one marker in a call), and Unredact restores a scrubbed request value before matching, so a committed tape still meets the test's real credential.

Readable bodies, stable order

PrettyJson(n) and PrettyXml(n) indent recorded bodies and canonicalize them for matching. Opt-in stable order sorts JSON keys, chosen arrays and response headers for services that answer in a different order each run, so a re-record is still byte-identical.

Matching and diagnostics

Strict method and path matching, opt-in header and body matching, order-independent MatchMultiple replay, and a playback range that replays a slice of a long tape. A mismatch report names the outcome, the closest candidate and the first real difference.

Drift detection

Fail-if-changed: a re-record writes the tape but flags any difference from the committed one, so CI catches an upstream change as a Git diff and a failing build — the TCK idea, built in.

Windows authentication: NTLM and Negotiate

Record mode pairs each client connection with an upstream connection of its own, so connection-bound authentication (NTLM, and Negotiate carrying NTLM, as with IIS, TFS, SharePoint and intranet WCF) records correctly. Pre-recorded NTLM tapes show what each leg of the handshake looks like and which rules make it replay.

.NET Framework 4.8

The one NuGet package serves .NET 8 and .NET Framework 4.8, including packages.config projects, and puts the right 64-bit engine (x64 or ARM64) in the output directory. A 32-bit build fails with a clear error, because there is no 32-bit engine. The package's tests run on Framework 4.8 too.
