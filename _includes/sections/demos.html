Servirtium VCR

One engine, many languages

servirtium-vcr is the current direction for Servirtium. Instead of a separate re-implementation per language, there is a single record/replay engine — Markdown parser/emitter, HTTP server, request matching, redaction, volatile-value handling and drift detection — written once in Aether, a language that compiles to C, and built as a native shared library with a plain C ABI. A thin FFI binding per language sits on top.

Because every language drives the same engine, cross-language compatibility is a build-time guarantee, not something each library re-derives and drifts on. Bindings carry no logic of their own. One monorepo, thirty languages (twenty-five native bindings plus Kotlin, Scala, Clojure, Groovy and F#, which ride on a sibling's), one build. The current release is 2.0.0-alpha.20.

Each language has its own page with exact install steps, copyable record and playback snippets and a prompt for your coding agent: see all thirty languages. All of them build and test through one aeb run against the shared libservirtium_vcr. Each binding's README has a runnable "Getting it" recipe and quick-start; see the monorepo README.

JVM family. The Java binding's jar also serves Kotlin, Scala, Clojure and Groovy — thin idiomatic layers (a Kotlin trailing-lambda DSL, a Groovy Closure DSL, Scala helpers, Clojure fns + with-open) over the same jar, with no second native FFI.

CLR family. F# uses the same .NET package through ordinary .NET interop, with loan-pattern combinators on top. The BEAM languages (Erlang, Elixir, Gleam, LFE) share one NIF, so a runtime family only has to be bridged once.

Platforms and packages

Every release is cross-built from one Linux host and published on GitHub by Actions, with a .sha256 beside each file. Nothing is on a language registry yet (PyPI's servirtium is the old 1.x package), so the install routes are the release assets and tags below.

Native libraries

  • Linux x86_64 and arm64, glibc and musl
  • macOS x86_64 and arm64
  • Windows x86_64 and arm64 (no 32-bit engine)
  • FreeBSD x86_64

Named libservirtium_vcr-<tag>-<os>-<arch>[-musl].{so,dylib,dll}. Most bindings load the one for your machine through SERVIRTIUM_VCR_LIB; the bundled packages find it themselves.

Multi-platform packages on the release page

  • Java: servirtium-vcr-<ver>.jar, six natives inside (not musl or FreeBSD)
  • .NET: Servirtium.Vcr.<ver>.nupkg, eight runtimes inside, for net8.0 and .NET Framework 4.8
  • Node: servirtium-vcr-<ver>.tgz, eight natives inside
  • Swift: an artifact bundle of static libraries (macOS, Linux glibc) that the repository's Package.swift downloads for you

Any other language: get-package.sh

One script, one language name, and you get the artifact your tooling expects with the engine already inside it: a wheel, gem, npm tarball, NuGet feed, jar, a relocatable tarball with a pkg-config file, or a source package with the library staged in. It installs the pinned toolchain first and runs no tests. 

curl -fsSL https://raw.githubusercontent.com/servirtium/servirtium-vcr/main/get-package.sh | sh -s -- ruby
# -> out/ruby/servirtium.gem, and the gem install line to run
